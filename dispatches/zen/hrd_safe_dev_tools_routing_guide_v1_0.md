### 🜂 HRD‑Safe Dev Tools Routing Guide (v1.0)

**Purpose:**  
Provide a clear, non‑commercial, HRD‑aligned path for using dev tools (VS Code, GitHub) without touching paid surfaces, misclassification risk, or unsafe support channels.

---

#### 1. Principles

- **No financial risk:** Avoid Codespaces, Azure DevOps, and any surface showing “paid” or “billing.”
- **No misclassification:** Do not route HRD‑aligned documentation through product‑idea or accessibility silos.
- **Full control:** Use tools that give you direct repo control without enterprise dependencies.
- **Non‑commercial:** Treat all work as protected research/HRD documentation, not as commercial development.

---

#### 2. Safe Tooling Surfaces

**Primary surface: VS Code Web (`github.dev`)**

- Free  
- Browser‑based  
- No billing  
- Full editor capabilities  

**Open via:**

```text
https://github.dev/<username>/<repo>
```

Example:

```text
https://github.dev/Borealiscodes/Zen-AI-Design-Architecture
```

---

#### 3. Safe Operations in VS Code Web

**File management**

- **Rename:** Right‑click file → *Rename*  
- **Move:** Drag file in Explorer → drop into target folder  
- **Create:** Right‑click folder → *New File* / *New Folder*  
- **Delete:** Right‑click → *Delete*

**Version control**

- Use the **Source Control** panel:
  - **Stage** changes  
  - **Write commit message**  
  - **Commit**  
  - **Sync / Push**  

All of this is free and does not touch paid infrastructure.

---

#### 4. Surfaces to Avoid (HRD‑Risk)

- **GitHub Codespaces**  
- **Azure DevOps**  
- **Enterprise support portals**  
- **Accessibility/product‑idea intake forms for HRD documentation**  

These surfaces:

- show paid indicators  
- are not designed for HRD‑aligned governance documentation  
- have already failed to route your materials safely

---

#### 5. Recommended Routing Pattern

1. **Architecture & governance work:**  
   Always in local editor or VS Code Web.

2. **Repo operations (PNG, markdown, specs):**  
   Always via VS Code Web.

3. **HRD documentation & evidence:**  
   Store in GitHub repos you control; do **not** submit via product or accessibility suggestion channels.

4. **Support / escalation:**  
   Use governance letters and formal escalation (we’ll design that in the third artifact), not frontline support queues.
